# mcppls 兼容性与稳定性加固设计

| | |
|---|---|
| 起因 | 用户在 openxlings/xlings 上验证临时版本：只有 `import` 能跳转，其余语义功能都不可用；每打开一个文件 CPU 骤升 |
| 目标 | 覆盖任何工程与环境；局部故障只影响出故障的地方；任何一步都不能卡住用户；资源占用让用户无感；日志与可观测性足以调试、捕获问题和接收用户反馈 |
| 日期 | 2026-09-15；第二轮 2026-09-16（打开构建描述之外的 `apps/gui/main.cpp` 时 clangd 单核空转；转到定义只到接口里的声明，见第 7 节） |

## 1. 现场证据（xlings，gcc 16.1 + libstdc++，24 个集合，884 个引擎条目）

修复前（29c11f2 的扩展，冷缓存，依次打开三个文件，探针 `lsp_probe.py`）：

| 打开 | 悬停 | 定义 | clangd 最忙一秒 | 扫描失败 |
|---|---|---|---|---|
| src/main.cpp | 240 s 无应答 | 无 | 27 核 | 5977 |
| src/core/config.cpp | 无应答 | 无 | — | — |
| src/core/xvm/commands.cpp | 无应答 | 无 | — | — |

VS Code 日志：12 秒 6003 次扫描失败、14 MB 日志；数据库在 884 与 481 条之间来回切换并反复重启 clangd。

故障链：

1. **兼容性缺陷（规划器）**：标准库单元取“第一个带标准库清单的单元”的参数。xlings 第一个集合是 C 库 `compat.mbedtls`，std 以 `-std=c11` 构建；C 源文件统一用 `clang++` 驱动，被当成 C++ 读。
2. **故障放大**：clangd 报 `Failed to build module std` 后，规划器把传递导入 std 的 288 个单元全部移出引擎数据库并重启 clangd，整个工程只剩 mcppls 引擎的模块名跳转。
3. **振荡**：任意保存清空失败记录 → 单元回到数据库 → 重启 → std 再失败 → 再移出 → 再重启。每次重启都丢掉全部模块构建，日志与扫描洪水占满 CPU。

只修第 1 点后（同一探针）：三个文件悬停 14.0 s / 3.0 s / 3.4 s 内有内容，定义正确，扫描失败 0，重启 0，日志 7 行；但冷启动第一次打开期间 clangd 用了 359 CPU 秒、最忙一秒 24.4 核（模块预热并行 15 路）。

## 2. clangd 23.1 故障模型（实验 `clangd_stall_probe.py`，每个场景独立进程，限时 10 s）

| 场景 | 被打开文件 | 其他文件 | clangd 日志 |
|---|---|---|---|
| S1 文件自身有无法解析的导入 | 正常 | 正常 | — |
| S3 导入一个编译出错的模块 | 正常 | 正常 | `Failed to build module e; due to Failed to compile …` |
| S4 模块自身编译出错 | 正常 | 正常 | — |
| S5 导入的模块不在数据库中 | 正常 | 正常 | — |
| S7 模块有两个提供者 | 正常 | 正常 | — |
| S10 普通单元导入不存在的模块 | 正常 | 正常 | `Don't get the module unit for module missing` |
| S11 实现单元的接口不在数据库中 | 正常 | 正常 | `Don't get the module unit for module k` |
| **S2 需要构建一个“自身导入无法解析”的模块** | **死锁（CPU 0）** | 需要构建模块的文件可能一并挂起 | 无任何失败行 |
| **S6 同上，隔两层** | **死锁** | 连普通文件也挂起 | 无 |
| **S12 运行中把一个已构建的模块改坏并移出数据库** | **死锁** | 普通文件挂起 | 无（clangd 内部仍记着旧的模块位置） |
| **S17 文件导入无人提供的模块，同时导入大型模块（xlings.core 等；命令是猜测的还是数据库中的都一样）** | **构建 AST 时空转，单核满载，永不结束** | 正常，但少一个工作线程 | `Failed to build module …; due to Don't get the module unit`，最后一行 `Building AST...`（见第 7.1 节） |

补充实验：`partition-implementation-exported-split` 审查（主接口 `export import` 了一个实现分区）在只修 C2–C4 后稳定等满 300 s 期限。逐文件定位到 `greet.cpp`（该模块自己的实现单元）：clangd 为它构建完前置模块（`hello.greet` 编译失败）后再无诊断，其他导入方 5 s 内都有诊断。最小化形态（S13 编译失败模块的实现单元、S14 导出实现分区的接口的实现单元、S15 其导入方、S16 接口本身，带或不带模块提示）在裸 clangd 中都不挂起，说明挂起需要更多条件叠加（`import std`、预热单元同时构建同一失败模块等）。不再追 clangd 内部原因，改为按证据隔离（C6）：该审查降到 13 s，且审查结果不完整的夹具现在判失败。

补充实验（`stub_probe.py`、`mask_probe.py`）：

| 做法 | 结果 |
|---|---|
| 只在交给 clangd 的文档里把无法解析的 import 换成空白 | 无效：clangd 按磁盘内容扫描依赖，一个前置模块失败后放弃全部前置模块，其他 import 也报找不到 |
| 为无人提供的模块写一个只含 `export module X;` 的占位单元并写入数据库 | 有效：导入它的模块、导入该模块的文件、文件本身全部正常悬停，没有诊断错误，没有死锁 |

结论：

- 唯一的死锁条件是 **clangd 需要构建一个导入无法解析（含传递）的模块提供者**。死锁不打印日志，只能由超时发现，而且会波及其他文件。
- 文件自身导入无法解析、导入编译出错的模块、编译错误，都不会挂起。
- 运行中提供者从“可构建”变为“不可构建”，只改数据库不够，必须重启 clangd。

## 3. 原则

| 编号 | 原则 |
|---|---|
| P1 | 故障只影响出故障的地方：一个模块失败，不移除与它无关的单元；导入它的普通单元仍由 clangd 服务 |
| P2 | 不排除单元，补上缺的部分：无人提供的模块由占位单元提供，每个 import 都能解析，死锁条件不再出现；排除只留给有证据的情形（重复提供者、缺 macOS SDK） |
| P3 | 重启是最后手段：只在仍被导入的模块换了单元或失去单元、或已有单元的编译参数变了时重启；有速率限制与指数退避；同一原因不振荡 |
| P4 | 每个请求有期限与退路；未知挂起按文件隔离，而不是停用整个引擎 |
| P5 | 兼容性靠构造保证，并有退路：命令按语言与导入方构造；工具链的 std 构建失败时退到语义工具包，而不是放弃导入 std 的所有文件 |
| P6 | 资源有界：模块预热并发、日志速率都有上限 |
| P7 | 降级可见：状态里写明哪些模块、多少文件、为什么降级 |

## 4. 方案

| 编号 | 改动 | 对应问题 |
|---|---|---|
| C1 | 规划器按单元语言选驱动（C 用 `clang`）；std 取导入 std 的 C++ 单元的参数，永不取 C 单元 | 兼容性缺陷（已完成） |
| C2 | 占位模块：无人提供（或 clangd 找不到其提供者）的模块，由缓存中只含 `export module X;` 的占位单元提供，每个 import 都能解析，不可构建的提供者不复存在，任何单元都不再因导入而离开数据库；只剩重复提供者的后者、缺 macOS SDK 的工具包单元离开。跳转结果中指向占位单元、预热单元的位置被去掉。编辑器打开的、没有任何集合描述的工作区 C++ 源文件（未启用的 feature 的目标、临时文件）也进入数据库：取路径最近的 C++ 单元的参数，导入照常解析或得到占位单元；数据库还没有、或刚加入它的文件，等 clangd 重读数据库后再交给 clangd（第 7.1 节） | 故障放大、S17 |
| C3 | 失败分类与记忆：`Don't get the module unit` 记为“无法解析”，`Failed to compile` 只是诊断；失败记录绑定提供者文件的指纹，只有该文件或其命令变化才清除 | 振荡 |
| C4 | 重启策略：仍被导入的模块换了单元或失去单元（S12），或已有单元的编译参数变了（切换上下文、构建参数变化，clangd 不为已打开的文档重读数据库）才重启；首次立即，之后间隔 10 s 起倍增，10 分钟内最多到 5 min；新增单元、占位模块增减、导入与提示变化不重启 | 重启风暴 |
| C5 | std 退路：工具链的 std 被判为无法解析或编译失败时，该上下文改用语义工具包规划，并报告 `std-fallback-kit` | std 失败拖垮全工程 |
| C6 | 看门狗：同一文件请求连续超时，隔离该文件（交给 mcppls 引擎应答），期满、计划给了它不同的命令、或它的导入与模块声明变了才交还（模块编译失败引起的隔离在任意源文件保存时交还），已隔离文件迟到的超时不再重复隔离；隔离时 clangd 仍在处理该文件（`textDocument/clangd.fileStatus` 不是空闲或排队）则按闸门重启 clangd，收回空转的核与工作线程（第 7.1 节）；多个文件同时超时且 clangd 无应答，隔离最先被问到的文件并按退避重启；崩溃时隔离崩溃前正在处理的文件，五分钟内五次崩溃才停用引擎。诊断迟迟不来的文件：一个模块编译失败后，它的实现单元与分区 5 s 内没有诊断就隔离（见第 2 节 S13–S16 与审查实例）；任何文件 2 min 没有诊断且模块预热 1 min 无进展也隔离。无头流程（审查、校验）把隔离的文件视为 mcppls 引擎服务的文件，不再等待 | 未知挂起、崩溃 |
| C7 | 资源：clangd 工作线程（`-j`，同时限制后台索引）为物理核数的 1/4、至少 2；模块预热并发为其一半、有人等文件时为 1/4、至少 1；clangd 日志转发每 10 s 最多 40 行并汇总被略去的行数，详细日志（`--log-level debug`）不限 | CPU 骤升、日志洪水 |
| C8 | 状态：`unresolved-module`（带模块名）、`std-fallback-kit`、`file-quarantined`（文件数） | 降级不可见 |
| C9 | 可观测性（见第 5 节） | 调试、问题捕获、用户反馈 |
| C10 | 实现单元里的定义：clangd 对定义请求给出的位置都是模块接口或分区里的纯声明时，在 clangd 中不经编辑器打开该模块的其他单元，构建完（最多等 8 s）后再问一次（第 7.2 节） | 转到定义只到接口 |

## 5. 可观测性（已实现）

| 编号 | 内容 |
|---|---|
| O1 | 事件时间线：每个工作区保留最近 500 条带时间的关键事件——模型加载、计划应用（条目、占位、离开、问题数）、clangd 启动与重启（原因、是否被闸门推迟）、崩溃、请求超时（文件、方法、耗时）、文件隔离与归还、模块失败（种类、原因）、std 退到工具包、被限流的日志行数 |
| O2 | 持久日志：服务器日志带时间戳写入 `<缓存>/workspaces/<键>/logs/server.log`，按大小轮转，编辑器关闭后仍可取回 |
| O3 | 诊断报告：LSP 请求 `cxxModules/report`、命令行 `mcppls report`、VS Code 命令 “C++ Modules: Collect Diagnostic Report”，内容为版本与平台、模型与计划摘要（条目、占位模块、离开的单元与原因、问题）、引擎状态（重启次数与原因、隔离文件、找不到的模块、std 来源）、请求统计（按方法的次数、超时、耗时分位、由哪个引擎应答）、事件时间线、日志文件位置与末尾 |
| O4 | 编辑器：状态栏提示写明降级原因与规模；降级或错误状态且没有专门修复命令时，状态项的命令是收集报告 |

实现要点：日志行带 UTC 毫秒时间；`serve` 与 `mcp` 各写 `<缓存>/logs/<种类>-<时间>-<标记>.log`（5 MB 轮转，保留同类最新 10 份）；报告中每个根目录含模型、计划（占位模块、离开的单元、问题）、各引擎状态与详情（clangd：启动参数、重启历史、隔离文件、找不到的模块、编译失败的模块、std 来源、预热进度与上限、挂起请求数、被略去的日志行数）、按方法的请求统计（次数、空结果、错误、取消、p50/p95/最大耗时、应答引擎）、事件总数与最近 300 条事件，以及最近 300 行日志。一致性运行器新增 `report` 检查与 `max-items` 断言，`module-faults` 用它断言占位模块存在、全程无重启、无隔离文件。第二轮新增：计划的 `openSources`（构建描述之外、按最近单元规划的文件）；clangd 详情的 `filesWaitingForDatabase`、`fileStates`（clangd 对每个打开文件的最新状态）、`backgroundUnits`、`definitionSearches`；事件 `file-waits-for-database`、`file-given-to-engine`、`file-handed-back`（带原因）、`engine-restart-scheduled`、`definition-search`、`background-unit-stuck`，`file-set-aside` 带 clangd 当时的状态。

## 7. 第二轮（2026-09-16）

### 7.1 打开 `apps/gui/main.cpp` 时 clangd 单核空转

现场：xlings 的 `xlings-gui` 目标只在 `--features gui` 时构建（`required_features = ["gui"]`），`apps/gui/main.cpp`、它导入的 `xlings.ui.gui`（feature 依赖包 `apps/gui`）与 `imgui.app` 都不在 mcpp 的构建描述中，引擎数据库没有这个文件。clangd 为它从最近的条目插值出一条命令，两个导入无处解析。

定位（`gui_bisect.py`：变体写在原文件旁，给出 `src/main.cpp` 的命令，`clangd --check`，限时 90 s）：

| 变体 | 结果 |
|---|---|
| T1 只导入 std 与 xlings.core、xlings.platform、xlings.runtime | 完成 |
| T2 再加 `import xlings.ui.gui;`（无人提供），主体只有空的 `main` | 卡在 `Building AST...`，纯用户态 CPU，不结束 |
| T3 再用它的名字；T4 原文件去掉两个缺失导入；T5 原文件 | T3、T5 卡住；T4 完成 |
| T6 只导入 std 加原文件主体 | 完成 |
| 原文件加 `-fno-spell-checking` | 仍卡住 |
| 原文件不在数据库中（clangd 插值命令） | 同样卡住 |
| 原文件加占位模块，且数据库中有它的明确条目 | 9 s 完成 |

即第 2 节 S17（小模块下的 S10 不挂起）。构建描述中的单元导入无人提供的模块时 C2 已给出占位单元，只有构建描述之外的文件没有。旧版的隔离只是不再把文件发给 clangd，clangd 不会停下已经开始的构建，隔离后仍满载；文件一改动就交还 clangd，再次触发。

改动（C2、C6）：

- 工作区把编辑器打开的、在根目录内、构建描述没有的 C++ 源文件交给规划器（`PlanInput::openSources`）。规划器为它取共同目录最多的 C++ 单元的参数（同一集合、工作目录与驱动），按它自己的角色决定模块模式，扫描它的导入；无人提供的模块照常得到占位单元，照常加模块提示。这类文件在会话中保留（文件删除后移除），再次打开不改动数据库；模型改为描述它时由模型接管。
- clangd 23.1 最多每 5 s 检查一次 `compile_commands.json` 是否变化，之前交给它的文件用猜测的命令。引擎对数据库还没有的工作区 C++ 源文件先不打开，由 mcppls 引擎应答，工作区 100 ms 内重新规划；计划写入后，若 clangd 已读过旧数据库，文件在写入 6 s 后交给 clangd；计划没有接纳它就立即交给 clangd，最多等 15 s。首个计划之前 clangd 没读过数据库，不必等。
- 隔离：记录 clangd 当时对该文件的状态。因请求连续超时、或 2 分钟没有诊断而隔离，且 clangd 仍在 `parsing`/`running` 这个文件时，按重启闸门重启 clangd（新进程不打开已隔离的文件）。交还条件见 C6。

实测（温缓存，同一探针 `nav_probe.py`，先打开 `src/main.cpp` 等 25 s，再打开 `apps/gui/main.cpp`）：

| | 修复前（5024274） | 修复后 |
|---|---|---|
| 打开后 clangd 线程 | `Worker:main.cpp` 持续 1.0 核 | 空闲 |
| 悬停 `xlings::LogLevel` | 10 s 超时，无内容 | 1 s 时由 mcppls 引擎应答（空）；9 s 时 clangd 应答，内容正确 |
| 定义 `xlings::EventStream` | — | `src/runtime/event_stream.cppm:15`，0.0 s |
| 模型加载前就打开该文件 | — | 首个计划即包含它与两个占位模块，悬停 0.0 s 正确，无空转 |

`xlings.ui.gui` 与 `imgui.app` 中的名字（`Model`、`Panel`）仍然没有语义：它们在构建描述之外，占位单元只保证不挂起、其余名字可用。

### 7.2 转到定义只到 `.cppm` 里的声明

语义：LSP 的“转到定义”到定义（函数体），“转到声明”到声明；光标已在定义上时 clangd 给出声明，两者可以来回切换。clangd 与 VS Code C/C++ 扩展对头文件与源文件都是直接到实现，并不是先到接口、再点一次到实现。

原因：clangd 只在构建过的文件（打开的文件，或后台索引）里知道函数体的位置；clangd 23.1 的后台索引不能构建模块导入（“Failed to compile …, index may be incomplete”），实现单元里的定义进不了索引，实现单元没打开时，定义请求退回为接口里的声明。探针：从 `src/core/notice.cpp` 对 `diag::emit` 请求定义，得到 `src/core/diag.cppm:87`；打开 `src/core/diag.cpp` 后得到 `src/core/diag.cpp:66`。

改动（C10）：

- 规划器为每个条目记下它所属的模块（`EngineEntry::module`，接口、分区、实现单元都有）。
- clangd 对定义请求给出的每个位置都在模块接口或分区中、且是纯声明（名字之后在括号外先遇到 `;`，而不是函数体、初始化、`= default`、构造函数初始化列表或基类子句；注释与字符串不计）时，引擎在 clangd 中不经编辑器打开该模块的其他单元：实现单元先于分区，文件名与接口相同的、目录相近的在前，每次最多 4 个；它们构建完、或等满 8 s 后，再问一次，得到位置就用新的，否则用第一次的。编辑器已打开的单元不重复打开，还在构建的就等它。
- 这些后台单元的诊断不转发，关闭时 clangd 发出的空诊断也不转发；10 分钟不用关闭，最多 12 个，按最久未用淘汰；编译失败的模块、数据库刚加入的文件不后台打开；2 分钟没构建完的单元在它变化前不再后台打开，clangd 仍在处理它时按闸门重启；编辑器打开一个后台单元时先关闭，再作为编辑器的文档打开，诊断重新发布；clangd 重启时进行中的查找用第一次的结果应答。

实测（xlings，温缓存）：`diag::emit` 的定义 1.0 s 到 `src/core/diag.cpp:66`（后台构建 1011 ms），再问 0.0 s；转到声明仍到 `src/core/diag.cppm:87`。
